# 评测机制与使用

> 定位：eval 问答效果验证的**机制说明与使用指南**——怎么跑、怎么判分、产物怎么看。
> 分工：本文是机制与使用的唯一权威源；设计动机、21 题验证集的题型设计理由与解读细则见 [效果验证.md](效果验证.md)；工具目录内速查见 [eval/README.md](../eval/README.md)。

## 1. 组成与端到端流程

| 路径 | 说明 |
|---|---|
| `eval/corpus/` | 5 份固定评测语料（员工手册 / 行政管理制度 docx，预算表 / 价格表 xlsx，服务合同 pdf），由 `backend/src/test/java/com/docrag/evalcorpus/EvalCorpusTest.java` 生成、入 git |
| `eval/dataset.json` | 验证集：21 题 × 9 类题型，每题含 question、golden（正确总结答案）、可机判要点（keypoints 组内 any_of）、禁含项、拒答预期 |
| `eval/run_eval.py` | 评测 runner（用 `frontend/.venv` 运行，仅依赖 requests + 标准库；纯工具，不参与服务运行、不改生产代码） |
| `eval/results/` | 评测产物（gitignore）：`eval-<时间戳>.json` 全量原始 + `eval-<时间戳>.html` 人可读报告 |

```
preflight（GET /api/status + /api/ask/params；后端不可达 → 退出码 2）
  → 可选 --reset（交互确认 CLEAR / --yes → POST /api/admin/clear 全量清空，见 §3.4）
  → stage_corpus（按 filename 增量上传 5 份语料到真实库，幂等、绝不默认清理，见 §2.1）
  → 逐题 POST /api/ask（modes=plain,deep，每模式独立召回 + 独立 LLM，见 §2.2）
  → 两层判分（L1 确定性默认；L2 LLM 裁判可选，见 §2.3）
  → 控制台报告 + results/eval-<ts>.json + eval-<ts>.html；任一 L1 失败 → 退出码 1
```

## 2. 评测机制

### 2.1 语料常驻真实库

- runner 默认打**真实后端** `http://127.0.0.1:8080`（即仓库 `data/` 真实库）——5 份语料上传后常驻，与日常检索 / 问答共用同一份库，不建独立评测索引；
- staging 按 filename 增量：已在 plain、deep 两个索引中的文件跳过，不产生重复 docId；**绝不清理已有文档**，重复运行安全（幂等）；
- 历史评测曾用 `--backend` 指向临时冒烟实例（18080 等），语料是否在真实库以 `GET /api/status` 为准。

### 2.2 双模式独立作答

- 每题一次 `POST /api/ask`，`modes=plain,deep` 时两模式各自走完整生产链路（chunk 级混合召回 → 拼编号 prompt → **该模式独立调一次 LLM**），互不影响——被测对象与生产问答完全同链路；
- 单题超时默认 180s（`--timeout`）；全量 21 题 × 2 模式约 42 次 LLM 调用，数分钟。

### 2.3 两层判分

**L1 确定性判分（默认，主信号）**——判分前答案与关键点均过 normalize（全角转半角、去千分位逗号、去全部空白）：

1. **关键点组命中**：每题若干组、组内 any_of（如 `800000 | 80万 | 八十万`），默认全组命中才过；总结 / 列举题用 `min_hits` 放宽；
2. **禁含项**（forbidden）：答案不得包含的子串，防幻觉（如 D1 问「预算超 40 万的部门」，答案不得出现运营 / 人力 / 财务）；
3. **引用校验**：答案中每个 `[n]` 必须映射回响应 `chunks[].ref`；非拒答的实质答案须至少一个引用（引用契约）；
4. **拒答校验**（expect_refusal）：须命中拒答话术正则（资料不足 / 无法作答 / 未检索到…）且不泄露禁含项（I2 不得把 2026 年总额冒充 2027）。

**L2 LLM 裁判（`--judge`，可选）**：复用后端同一 LLM 配置（缺省取 application.yml 中 `docrag.llm.active` 选中 provider 的默认值，环境变量 `DOCRAG_LLM_BASE_URL / DOCRAG_LLM_API_KEY / DOCRAG_LLM_MODEL` 可整体覆盖），温度 0，按 golden 打分：`2=正确且完整；1=部分正确；0=错误或不当拒答`，附一句话理由；拒答题（I 组）不送裁判。

L1 可复现是主信号；L2 弥补关键点覆盖不到的措辞差异，两层结果分列、不互斥。

### 2.4 退出码

`0` 全部 L1 通过；`1` 任一 L1 失败；`2` 后端不可达。完整回归（非效果验证）用 `cd backend && mvn test`、`cd frontend && pytest`。

## 3. 使用方法

### 3.1 前置条件

1. 后端已启动（默认 `http://127.0.0.1:8080`，须从 `backend/` 目录启动，见 [运维与启动.md](运维与启动.md)）；
2. 建议 vector-service 也启动——语义改写类（F 组）依赖向量召回，不可用时结果按 `degraded` 标注解读；
3. LLM 可达（`application.yml` 的 `docrag.llm.*`）；`--judge` 时 runner 直接复用同一配置。

### 3.2 常用命令

```bash
# 全量（双模式 + LLM 裁判）
frontend/.venv/bin/python eval/run_eval.py --judge

# 只跑 L1（不调裁判，LLM 调用量减半）
frontend/.venv/bin/python eval/run_eval.py

# 子集 / 单模式 / 按题型
frontend/.venv/bin/python eval/run_eval.py --filter A1,F1 --modes deep
frontend/.venv/bin/python eval/run_eval.py --filter-type 表格聚合统计
```

### 3.3 参数一览

| 参数 | 默认 | 说明 |
|---|---|---|
| `--backend` | `http://127.0.0.1:8080` | 后端地址（默认即真实库） |
| `--modes` | `plain,deep` | 参评模式逗号串 |
| `--filter` / `--filter-type` | 无 | 按题 id（如 `A1,F1`）/ 按题型子串过滤 |
| `--judge` | 关 | 启用 L2 LLM 裁判 |
| `--timeout` | 180 | 单题 ask 超时秒数（双模式两次 LLM 串行） |
| `--dataset` / `--corpus` / `--output` | `eval/` 内置 | 题集 / 语料 / 结果目录 |
| `--reset` / `--yes` | 关 | 评测前全量清空（危险，见 §3.4） |

### 3.4 --reset（危险）

`--reset` 会在评测前调 `POST /api/admin/clear` 全量清空：双倒排索引 + 双向量 collection + **全部上传原文件（含非评测语料的用户文档，不可恢复）**；需交互输入 `CLEAR` 确认（脚本场景用 `--reset --yes`）。

仅在这类场景使用：索引里存在与语料同名但内容不同的旧文件（staging 按 filename 跳过上传会评到旧内容）、或想要绝对干净的评测基线。

### 3.5 语料再生成

```bash
export JAVA_HOME="$(brew --prefix openjdk@17)/libexec/openjdk.jdk/Contents/Home"
cd backend && mvn test -Dtest=EvalCorpusTest
```

**语料内容与 dataset.json 的 golden 答案强耦合，改语料必须同步改题集**。PDF 依赖系统中文字体（macOS：`/System/Library/Fonts/Supplemental/Arial Unicode.ttf` 等），缺失时生成器直接 fail（不做英文回退，回退会破坏金答案）。

## 4. 结果产物与解读

| 产物 | 说明 |
|---|---|
| `eval-<ts>.json` | 全量原始（机器可读，schema 稳定）：`backend / modes / judge / ask_params / vector_available / stats / results`，含每模式 answer、chunks（全部召回原文）、l1 / l2 明细 |
| `eval-<ts>.html` | 人可读报告（单文件自包含，浏览器直接打开），结构见下 |

HTML 报告结构：

- **页头**：backend / modes / judge / ask 参数 / vector 可用性（不可用时顶部红横幅提示 F 组失败属预期）；
- **总览卡片**：每模式 L1 通过率（按百分比绿 / 黄 / 红着色）、degraded 数、L2 均分；
- **题型 × 模式矩阵**：单元格按通过比例着色（全过绿 / 部分黄 / 全败红），plain 与 deep 的强弱项一眼可见；
- **逐题明细**：每模式 PASS / FAIL / ERR 徽章 + L2 分值徽章 + degraded 标记；**任一模式失败时，该题所有模式（含通过的一侧）均可展开「详情」**——L1 失败原因（缺失关键点 / 禁含项 / 无效引用）、答案全文、golden 对照、召回 chunks 表（ref / 文件 / 来源 / score / 原文），对照两侧召回差异即可定位失败根因（如 plain 聚合题只召回到表头、deep 召回整表）。

解读细则（plain 聚合类失败 ≠ bug、degraded 语义、forbidden 从严）见 [效果验证.md](效果验证.md) §5。
