# 召回方式与降级语义 —— 问答为何不走向量、各模式检索的召回方式

> 本文说明 doc-rag 各链路的召回方式与 vector-service 的失败语义。
> 模式概念：**plain（纯文本解析）/ deep（深度解析）**，各有一套倒排索引与各自的向量 collection（`docrag_plain` / `docrag_deep`）。

## 1. `/api/ask` 为什么不走向量服务

这是一条设计约束，不是巧合。看 `AskService` 的编排流程（`backend/src/main/java/com/docrag/ask/AskService.java`），问答的上下文召回是这样做的：

```
问题 + docIds（用户勾选的文档） + modes
        │
        ▼
topDocsByDocIds(question, docIds, topN)   ← 纯 BM25，且限定在这些 docId 内（每模式独立执行）
        │
        ▼
查询时切块（plain: Chunker.chunk / deep: chunkKeepingTables）
        │
        ▼
按「问题与块的分词重叠度」选 top-K（双模式配额减半、每模式保底 2 块）→ 拼 prompt → 调 LLM
```

关键点在 `topDocsByDocIds`：**问答的检索范围已经被用户勾选的 docIds 收窄了**，BM25 只需在几篇文档内排序，召回不是瓶颈。而向量召回的强项是「全库范围下语义相近但词面不同的文档」——范围已经收窄到勾选的文档后，这个优势用不上，反而在编排里多一个可失败的外部依赖（问答本身已经有 LLM 这个会失败的环节了）。架构文档（CLAUDE.md）里也因此明确写了「LLM 失败整体报错，不降级编造」——问答链路的失败语义是严格的，BM25 无外部依赖、确定性可复现，适合这条链路。

## 2. 各模式检索的召回方式

`GET /api/search` 对每个选中模式独立执行混合检索：

| 链路 | 召回方式 | 依赖 vector-service？ |
|---|---|---|
| 检索 `mode=plain` | BM25 + `docrag_plain` 向量 RRF 融合 | 读路径：可降级（`degraded=true`） |
| 检索 `mode=deep` | BM25 + `docrag_deep` 向量 RRF 融合（chunk = 统一文本块感知切块，表格含标题行整体保留） | 读路径：可降级（`degraded=true`） |
| 问答（任何 modes 组合） | 勾选范围内 BM25 → 查询时切块 → top-K | 否 |

两模式的向量 collection 语料不同（plain=纯文本 chunk、deep=统一文本块感知切块），但共用同一个 bge 编码模型与同一个 vector-service 进程。

## 3. vector-service 不可用时的的影响面

8081 挂掉时：

- **检索**（任何模式）：该模式向量查询失败 → `degraded=true`，纯 BM25 继续返回，不报错；
- **上传**：写路径失败上抛 → 本次入库已写库逆序回滚，上传失败；
- **一键清理**：直接 400 拒绝（只清倒排会残留向量幽灵命中）；
- **问答**：完全不受影响（纯 BM25 召回，不依赖向量服务）。
