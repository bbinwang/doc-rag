# 召回方式与降级语义 —— 各链路（检索/问答）的召回方式与向量失败语义

> 本文说明 doc-rag 各链路的召回方式与 vector-service 的失败语义。
> 模式概念：**plain（纯文本解析）/ deep（深度解析）**，各有一套倒排索引与各自的向量 collection（`docrag_plain` / `docrag_deep`）。

## 1. 问答（`/api/ask`）的召回方式：chunk 级 BM25 + 向量 RRF

问答是**全库检索**（不选文档），每模式独立执行 chunk 级混合召回（`ModeSearcher.recallChunks`）：

```
问题 + modes
        │
        ▼
每模式独立（plain / deep 各一套）：
  ① BM25 路：全库 doc 召回 pool=clamp(bm25Chunks, 5, 20) 篇
     → 按与入库一致的切块策略查询时切块（plain: Chunker.chunk / deep: chunkKeepingTables(256)）
     → 与问题分词重叠度排序（score>0）取前 bm25Chunks 个 chunk
  ② 向量路：vector-service 该模式 collection topK=vectorChunks
  ③ 两路按 (docId, chunk 精确文本) 去重 → chunk 级 RRF（k=60）融合
        │
        ▼
重排后按 contextChunks + 字符预算截断 → 拼 prompt → 该模式独立调一次 LLM
```

**去重成立的前提**：检索期切块与入库期切块完全一致（`IngestService` 与 `ModeSearcher.chunkForMode` 同一套 `Chunker` 调用），BM25 路查询时切块与向量库 chunk 逐字节同源，精确文本去重可靠。

**为什么向量路不再被 overlap 过滤淘汰**：旧版问答是「勾选文档范围内 BM25 + 分词重叠度排序」，`score=0` 的 chunk 不入选——语义相近但词面不重叠的 chunk 会被误杀。重构后向量路召回的 chunk 不参与 overlap 过滤，直接进 RRF 融合，`source=vector` 的 chunk 也能成为上下文。

## 2. 各链路召回方式对比

| 链路 | 召回方式 | 依赖 vector-service？ |
|---|---|---|
| 检索 `GET /api/search`（每模式） | docId 级：BM25 + 该模式向量 RRF 融合（RRF_POOL=50） | 读路径：可降级（`degraded=true`） |
| 问答 `POST /api/ask`（每模式） | chunk 级：BM25 路（doc 召回→切块→overlap 排序）+ 向量路，chunk 级 RRF 融合 | 读路径：可降级（`degraded=true`） |

两模式的向量 collection 语料不同（plain=纯文本 chunk、deep=统一文本块感知切块），但共用同一个 bge 编码模型与同一个 vector-service 进程。

## 3. vector-service 不可用时的影响面

8081 挂掉时：

- **检索**（任何模式）：该模式向量查询失败 → `degraded=true`，纯 BM25 继续返回，不报错；
- **问答**（任何模式）：该模式向量路失败 → `degraded=true`，纯 BM25 路 chunk 照常召回作答（与检索一致的降级语义）；
- **上传**：写路径失败上抛 → 本次入库已写库逆序回滚，上传失败；
- **一键清理**：直接 400 拒绝（只清倒排会残留向量幽灵命中）。

## 4. 问答的 LLM 失败语义

- 某模式召回 0 chunk → 该模式返回占位提示「未检索到…无法作答」，**不调 LLM**，另一模式照常；
- LLM 调用失败**按模式隔离**：失败模式 `answer=null + error`（chunks/docs 照常返回供调试），HTTP 200；仅当**全部**选中模式的 LLM 调用都失败才整体 500；
- LLM 未配置（apiKey 为空）→ 400，不发起任何调用。
