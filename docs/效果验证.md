# 问答效果验证

> 目标：回答「plain / deep 两模式在同一组问题下各自答得怎么样」「表格类问题 deep 是否真的优于 plain」。
> 落地：[`eval/`](../eval/)——固定语料 + 验证集 + 独立评测 runner（纯工具，不参与服务运行，不改任何生产代码）。
> 评测机制细节与使用方法见 [评测机制与使用.md](评测机制与使用.md)；本文聚焦设计动机与结果解读。

## 1. 为什么需要效果验证

问答链路的现有测试（AskServiceTest 等）全部打桩 LLM，验证的是**编排正确性**（调用次数、prompt 组装、失败隔离、引用映射），不是**答案质量**。效果验证回答的是另一类问题：

- 双模式在同一问题上各自表现如何，差异在哪类题型上；
- 混合召回（BM25 + 向量 RRF）对语义改写类问题是否真的有效；
- 拒答契约（资料不足时明说、不编造）是否被 LLM 遵守。

## 2. 组成与流程

```
eval/corpus/（5 份固定语料，Java 生成器产出、入 git）
        │  runner 按 filename 增量上传（POST /api/documents，已在两索引的跳过）
        ▼
eval/dataset.json（21 题：question + golden + 可机判要点）
        │  逐题 POST /api/ask（modes=plain,deep，每模式独立作答）
        ▼
两层判分 → 控制台 + results/ 报告（type × mode 通过率矩阵）
```

人可读报告为**单文件 HTML**（`results/eval-<时间戳>.html`）：总览卡片（每模式 L1 通过率 / degraded 数 / L2 均分）+ 题型 × 模式通过率矩阵（单元格按命中比例绿/黄/红着色）+ 逐题明细表（每模式 PASS/FAIL/ERR 徽章，FAIL 可展开失败原因、答案与 golden 对照、top chunks）。`results/eval-<时间戳>.json` 保留全量原始数据（机器可读，schema 不变）。

语料生成器：`backend/src/test/java/com/docrag/evalcorpus/EvalCorpusTest.java`（`mvn test -Dtest=EvalCorpusTest`，POI + PDFBox，PDF 无中文字体直接 fail 不回退英文）。**语料内容与 dataset.json 的 golden 强耦合，改任一侧必须同步另一侧。**

## 3. 验证集设计（21 题 × 9 类）

| 题型 | 题数 | 考察点 | plain/deep 预期差异 |
|---|---|---|---|
| 单点事实（A） | 3 | 正文散文事实定位 | 无差异：事实独立成段，plain 128 字符块内完整 |
| 表格数值定位（B） | 3 | 表格单元格定位 | 无差异：plain 下 xlsx 每行独立块、行内不截断 |
| 表格聚合统计（C） | 3 | 全表求和/最值/差值 | **deep 优势**：整表一块；plain 行块多，受 bm25Chunks=5 召回预算限制只见部分行 |
| 表格条件筛选（D） | 2 | 多行过滤 | 同上，deep 优势 |
| 跨文档综合（E） | 2 | 两份文档事实合并 | 依赖 contextChunks=8 内同时召回两文档 chunk |
| 语义改写（F） | 3 | 词面零重叠（如「不打算干了…提早多长时间告知」→「离职提前三十日书面通知」） | 依赖向量召回；vector 不可用（degraded）时失败属预期 |
| 总结归纳（G） | 1 | 文档主旨概括 | 无显著差异（min_hits 放宽判分） |
| 多点列举（H） | 2 | 枚举全部条目 | 手册类六项同段 plain 可覆盖；表格行枚举 deep 优势 |
| 无答案拒答（I） | 2 | 资料不足时明说不编造 | 无差异；I2 额外校验不把 2026 数据冒充 2027 |

刻意设计的对照：A2（直述）与 F2（改写）同事实，量化 BM25 与向量路的差异。

## 4. 两层判分

### L1 确定性判分（默认）

1. **关键点组**：每题定义若干组，组内 any_of（如 `800000 | 80万 | 八十万`）；默认全组命中才过，总结/列举题用 `min_hits` 放宽。判分前答案与关键点均过 normalize（全角转半角、去千分位逗号、去全部空白），应对「1000000 / 100万 / 3,010,000 / １５ 个工作日」等写法差异。
2. **禁含项**（forbidden）：答案不得包含的子串，防幻觉（如 D1 问「预算超 40 万的部门」，答案不得出现运营/人力/财务）。
3. **引用校验**：答案中每个 `[n]` 必须映射回响应 `chunks[].ref`；非拒答的实质答案须至少一个引用（系统 prompt 的引用契约）。
4. **拒答校验**（expect_refusal）：须命中拒答话术正则（资料不足/无法作答/未检索到…）且不泄露禁含项（I2 不得输出 2026 年总额冒充 2027）。

L1 失败 → runner 退出码 1；后端不可达 → 2。

### L2 LLM 裁判（`--judge`）

复用后端同一 LLM 配置（缺省取 application.yml 中 active provider 的默认值，环境变量 `DOCRAG_LLM_BASE_URL / DOCRAG_LLM_API_KEY / DOCRAG_LLM_MODEL` 可整体覆盖），温度 0，按 golden 打分：`2=正确且完整；1=部分正确；0=错误或不当拒答`，附一句话理由。拒答题不送裁判。

L1 是主信号（可复现）；L2 弥补 L1 关键点覆盖不到的措辞差异，两层结果在报告中分列、不互斥。

## 5. 结果解读须知

- **plain 在聚合/筛选题上失败 ≠ bug**：plain 模式 xlsx 每行独立 chunk（行内不截断，定位题可过），但聚合需全部行同入上下文，`bm25Chunks=5`（默认）召回预算下只能看到部分行——这是「召回预算下的模式差异」，正确解读是调大 `bm25-chunks`/`context-chunks` 参数复测或使用 deep 模式，而非切块错误。
- **degraded 标注**：vector-service 不可用时该模式自动降级纯 BM25，语义改写类（F 组）失败属预期，报告按 degraded 分列。
- **forbidden 从严**：D 组若答案以排除句式提及非命中项（「运营部未超过」）会判失败，属刻意从严，failure 明细可人工复核。
- **HTML 报告**：`results/eval-<时间戳>.html` 用颜色区分 pass/fail/degraded/L2 分值，逐题可展开失败原因（L1 失败项、缺失关键点、无效引用）与 top chunks；vector 不可用时顶部红横幅提示 F 组失败属预期。
