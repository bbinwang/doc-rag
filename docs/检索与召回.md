# 检索与召回 —— search() 与 recallChunks() 两条链路、RRF 融合、降级语义

> 本文回答：检索页和问答页各走怎样的召回链路？为什么 RRF 只看排名？vector-service 挂掉时四条链路各自发生什么？
> 实现：`backend/src/main/java/com/docrag/searcher/ModeSearcher.java`（`RRF_POOL=50`、`RRF_K=60`）。
> 本文吸收自原《检索接口契约与全链路》《召回方式与降级语义》两文（已删除，git 历史可查）；API 字段级契约见《[api.md](api.md)》。

## 1. 两条链路一张图

```
                        检索页 GET /api/search                      问答页 POST /api/ask
                        ─────────────────────                      ─────────────────────
粒度                    docId 级                                   chunk 级
入口                    ModeSearcher.search()                      ModeSearcher.recallChunks()
BM25 路                 MultiFieldQueryParser 查 filename+content  全库 doc 召回 pool=clamp(bm25Chunks,5,20) 篇
                        top 50（RRF_POOL）                          → 入库同款切块 → 与问题分词重叠度排序取前 bm25Chunks
向量路                  vectorClient.query(mode, q, topK=50)       vectorClient.query(mode, q, topK=vectorChunks)
融合                    docId 级 RRF(k=60)                         (docId, chunk 精确文本) 去重 → chunk 级 RRF(k=60)
输出                    分页 hits + 高亮 snippet                   截断后的 chunks（调用方按 contextChunks/字符预算再截）
```

plain 与 deep 各一个 `ModeSearcher` 实例，跑完全相同的流程，只差索引目录与 collection。

## 2. search() 四步（检索页）

1. **BM25 召回**：一文一 Document，`MultiFieldQueryParser` 搜 `filename`+`content` 两字段（查询侧 IK 智能切分），取 top 50 池子；`Highlighter`（`SimpleFragmenter` 160 字符）生成带 `<em>` 的 snippet。
2. **向量召回**：同一 query 发 vector-service 该模式 collection（topK=50）；**同一 docId 多个 chunk 只保留最靠前的**（`putIfAbsent`）。服务不可用/超时 → 该模式 `degraded=true`，纯 BM25 继续，不影响另一模式。
3. **RRF 融合**：不比较两路原始分数（BM25 分数与余弦相似度量纲不可比），只看排名——`score = Σ 1/(k + rank)`，k=60。两路都命中的文档分数自然最高。原理与 k=60 出处见《[RRF融合与K常数](RRF融合与K常数.md)》。
4. **分页组装**：BM25 有命中 → 用 BM25 的 snippet（有高亮），`source`= both/bm25；**仅向量命中**（语义相似但关键词没匹配上，RRF 的价值所在）→ 回读倒排（`getById`）补 filename/path/type 元数据，snippet 用 chunk 原文（HTML 转义、无高亮），`source=vector`。`total` = 融合后去重 docId 总数（分页前）。

### snippet 的高亮与转义

BM25 路：`Highlighter` 输出「文本 + 成对 `<em>`」交替结构，经 `escapeKeepEm()` 对原文 HTML 转义但保留高亮标记；content 无命中词（如仅文件名命中）时回退开头 160 字符截断。仅向量路：chunk 原文整体转义、无高亮。前端对 snippet `|safe` 直接渲染（信任后端输出）。

## 3. recallChunks()（问答页，全库 chunk 级）

```
问题 + bm25Chunks + vectorChunks
  ① BM25 路：全库 doc 召回 pool=clamp(bm25Chunks, 5, 20) 篇（含 content 全文）
     → 按「入库同款切块策略」查询时切块（plain: chunk(128) / deep: chunkKeepingTables(256)）
     → 每 chunk 与问题分词求 Jaccard 重叠度（overlap），score>0 保留
     → 按 score 降序、doc rank 升序，取前 bm25Chunks 个
  ② 向量路：vectorClient.query(mode, q, vectorChunks)
  ③ 两路按 (docId, chunk 精确文本) 去重 → chunk 级 RRF(k=60) 融合
  → 返回 ChunkRecall(chunks, degraded)；仅向量命中的文档回读索引补 path
```

设计取舍：

- **去重成立的前提**：检索期切块与入库期切块逐字节同源（`IngestService` 与 `chunkForMode` 同一套 `Chunker` 调用），详见《[解析与入库](解析与入库.md)》§4.3。
- **为什么向量路不做 overlap 过滤**：旧版问答「分词重叠度排序」会把语义相近但词面不重叠的 chunk 误杀（用户问「试用期上限」，文档写「不超过六个月」）。重构后 overlap 只用于 BM25 路**内部排序**，向量路召回直接进 RRF，`source=vector` 的 chunk 也能成为 LLM 上下文。
- **为什么 BM25 路先召回 doc 再切块**：Lucene 索引是 doc 粒度的，chunk 只存在于向量库与查询时重切。先 doc 召回控制读全文的规模（pool 5-20 篇），切块后靠 overlap 精选出真含答案词的块。

## 4. vector-service 不可用：降级语义矩阵

8081 挂掉时，四条链路行为不同——**读路径降级、写路径拒绝**：

| 链路 | 行为 | 理由 |
|---|---|---|
| 检索（任何模式） | 该模式 `degraded=true`，纯 BM25 正常返回 200 | 关键词检索是主体，语义召回是增强 |
| 问答（任何模式） | 该模式 `degraded=true`，BM25 路 chunk 照常召回作答 | 同上；degraded 提示用户答案未受益于语义召回 |
| 上传入库 | 写路径失败上抛 → 已写库逆序回滚，上传报错 | 双库不一致会造成「倒排有、向量无」的静默缺失 |
| 一键清理 | 直接 400 拒绝，不做部分清理 | 只清倒排会残留向量 → 幽灵命中（向量召回到回读失败的结果） |

`degraded` 是 **per-mode** 的：vector-service 整体不可用时 plain/deep 各自标记各自降级，接口本身 200。

## 5. 两个易混点

- **检索与问答是两条独立链路**：都走 BM25+向量双路 + RRF(k=60)，但粒度（docId vs chunk）与用途（列表展示 vs LLM 上下文）不同。问答的 LLM 编排见《[问答设计](问答设计.md)》。
- **`search()` 不做 docIds 过滤的历史**：旧版选文档问答曾按 docIds 过滤；现行两条链路均为全库（问答页不选文档）。
