# 检索接口契约与全链路 —— GET /api/search 的请求响应格式与内部处理

> 本文整理检索接口（`GET /api/search`）的后端返回格式（后端 → 前端）与全链路处理流程（前端 → Flask → Java 后端 → vector-service）。
> 模式概念：**plain（纯文本解析）/ deep（深度解析）**，检索按模式独立执行，双模式时结果分模式返回、前端两栏对比。

## 1. 后端返回给前端的格式

后端返回的是**统一嵌套的按模式分组的 JSON**（`backend/src/main/java/com/docrag/api/SearchController.java` + `searcher/SearchResponse.java` / `SearchHit.java`）：

```json
{
  "modes": {
    "plain": {
      "total": 12,
      "degraded": false,
      "hits": [
        {
          "docId": "uuid",
          "filename": "xx.docx",
          "path": "data/upload/xx.docx",
          "type": "docx",
          "snippet": "…其中<em>合同条款</em>约定…",
          "score": 3.42,
          "source": "both"
        }
      ]
    },
    "deep": { "total": 8, "degraded": true, "hits": [ ... ] }
  }
}
```

要点：

- **外层只有一个 `modes` key**，内层 key 是模式 id（`plain` / `deep`），顺序 = 请求中 `modes` 参数的顺序（`LinkedHashMap` 保证，见 `SearchController.search()`）。
- **单双模式同构**：只选一个模式时形状完全一样，只是 `modes` 里少一个 key；空查询（`q` 为空白）时每模式返回 `{total: 0, hits: [], degraded: false}`。
- 每模式三个字段：
  - `total`：该模式融合去重后的命中文档总数（分页前）；
  - `degraded`：该模式向量服务不可用、已降级纯 BM25 时为 `true`（**per-mode**，不是全局）；
  - `hits`：当前页结果。
- 每条 hit：`docId` / `filename` / `path` / `type` / `snippet` / `score` / `source`：
  - `snippet` 是 **HTML 片段**（原文已 HTML 转义，命中词用 `<em>` 包裹），前端直接 `|safe` 渲染；
  - `score` 是 RRF 融合分（不是 BM25 原始分，与余弦相似度也不可比）；
  - `source` 取值 `both` / `bm25` / `vector`，标明该文档的召回来源。
- `page` 从 1 开始、对每模式独立生效（双模式共享 `page`，各栏显示各自 total）；`size` 后端钳制在 1–50。
- 前端 Flask（`frontend/app.py`）只原样转发这个 JSON，不改变形状；页面按模式渲染，双模式两栏对比。

## 2. 请求契约

```
GET /api/search?q=关键词&page=1&size=10&modes=plain,deep
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `q` | 必填 | 检索词；空白时每模式返回空结果（不报错） |
| `page` | 1 | 从 1 起，对每模式独立生效，双模式两栏共享同一页码 |
| `size` | 10 | 后端钳制 1–50 |
| `modes` | `plain` | repeated 或逗号串（`plain,deep`），非法值 400 |

前端 Flask 转发细节（`app.py`）：`size` 固定传 `PAGE_SIZE`、`timeout=10`；两栏用「任一模式结果超出本页即有下一页」判断翻页按钮。

## 3. 内部处理全链路（ModeSearcher.search()）

plain / deep 各一个 `ModeSearcher` 实例，跑完全相同的四步流程：

```
① BM25 召回                    ② 向量召回                      ③ RRF 融合                ④ 分页组装
MultiFieldQueryParser    +     vectorClient.query(mode,    →   score = Σ 1/(60+rank)   →   融合排序后切片
查 filename+content            q, topK=50)                     两路各按排名贡献           补 snippet/source
（查询侧 IK 智能切分）          查 docrag_{mode} collection
```

关键细节（行号指 `backend/src/main/java/com/docrag/searcher/ModeSearcher.java`）：

1. **BM25 路**（`:81-94`）：一文一 Document，`MultiFieldQueryParser` 搜 `filename`+`content` 两字段，取 top 50 池子（`RRF_POOL`），直接用 `Highlighter`（`SimpleFragmenter` 160 字符）生成带 `<em>` 的 snippet，按 docId 去重进 map。
2. **向量路**（`:96-106`）：同一 query 发给 vector-service 该模式 collection（`POST /query`，`topK=50`）；**同一 docId 多个 chunk 只保留最靠前的**（`putIfAbsent`）。服务不可用/超时 → 该模式 `degraded=true`，纯 BM25 继续，不影响另一模式。
3. **RRF 融合**（`:108-121`）：不比较两路原始分数（BM25 分数和余弦相似度不可比），只看排名——每个 docId 的融合分 = BM25 排名贡献 + 向量排名贡献之和，`k=60` 平滑（`RRF_K`）。两路都命中的文档分数自然最高。
4. **分页组装**（`:123-144`）：
   - BM25 有命中 → 用 BM25 的 snippet（有高亮）；`source` = 两路都命中 `both` / 只 BM25 `bm25`。
   - **仅向量命中**（语义相似但关键词没匹配上，RRF 融合的价值所在）→ 回读倒排索引（`getById`）补 filename/path/type 元数据，snippet 用 chunk 原文（HTML 转义、无高亮），`source=vector`。
   - `total` = 融合后去重 docId 总数（分页前）。

## 4. snippet 的高亮与转义

- BM25 路：`Highlighter` 输出「文本 + 成对 `<em>` 标签」交替结构，经 `escapeKeepEm()`（`ModeSearcher.java:227-240`）对原文做 HTML 转义但保留高亮标记；content 无命中词（如仅文件名命中）时回退为开头 160 字符截断。
- 仅向量路：chunk 原文整体转义，无 `<em>` 高亮。
- 前端对 snippet `|safe` 直接渲染（信任后端输出）；deep 栏若 snippet 是 markdown 表格，由前端 JS 渲染为 HTML table，否则回退纯文本。

## 5. 两个易混点

- **检索与问答是两条独立链路**：`/api/search` 是 docId 级 BM25 + 向量 RRF 融合（`search()`，RRF_POOL=50）；`/api/ask` 是 chunk 级混合召回（`recallChunks()`，BM25 路 doc 召回→入库同款切块→overlap 排序 + 向量路，chunk 级 RRF 融合）→ 每模式独立调 LLM。两者都走 BM25+向量双路，但粒度（docId vs chunk）与用途（列表展示 vs LLM 上下文）不同。问答链路的细节见《[召回方式与降级语义](召回方式与降级语义.md)》。
- **degraded 是 per-mode 的**：vector-service 整体不可用时，plain/deep 两模式各自标记 `degraded=true` 并各自降级，接口本身仍正常返回 200。
