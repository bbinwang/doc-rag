# RRF 融合与 RRF_K=60 常数解析

> 对应实现：`backend/src/main/java/com/docrag/searcher/ModeSearcher.java`（`RRF_POOL=50`、`RRF_K=60`）

## 融合逻辑

检索时每路召回最多取 50 名（`RRF_POOL`），按文档 docId 合并，每个文档在某一路的贡献只取决于它在**该路的排名**（rank 从 1 计），最后两路得分相加：

```java
// ③ RRF 融合：score = Σ 1/(k + rank)
rrf.merge(id, 1.0 / (RRF_K + rank++), Double::sum);   // BM25 路
rrf.merge(id, 1.0 / (RRF_K + rank++), Double::sum);   // 向量路
```

## 1. 为什么用「排名」而不是「分数」直接加

BM25 分数和向量余弦相似度是**两种不可比较的量纲**：

- BM25 分数无上限，随文档长度、词频波动（可能是 3.42，也可能是 30）
- 余弦相似度在 0~1 之间

直接 `bm25Score + cosine` 等于让 BM25 恒定碾压向量。RRF（Reciprocal Rank Fusion，倒数排名融合）的做法是**只看每一路内部的排名位置，完全丢弃原始分数**——天然无量纲问题，不需要任何分数归一化调参。这就是它成为混合检索标配的原因（Elasticsearch、Vespa 默认都是 RRF）。

## 2. k=60 是干嘛的：平滑常数

每个文档在某一路的贡献是 `1/(k + rank)`，k 控制头部位次的**优势衰减速度**：

| rank | k=60 时得分 | k=0（极端对比） |
|---|---|---|
| 1 | 1/61 ≈ 0.0164 | 1.0 |
| 10 | 1/70 ≈ 0.0143 | 0.1 |
| 50 | 1/110 ≈ 0.0091 | 0.02 |

- **k 越小** → 第 1 名对后面断崖式领先，「第一名说了算」
- **k 越大** → 曲线越平，深处的命中也有话语权

k=60 时第 1 名的得分只约是第 50 名的 1.8 倍——融合主要看**「你在几路里都靠前」**，而不是「你是不是某一路的冠军」。

## 3. 例子（对应搜索响应里的 `source` 字段）

某文档：BM25 排第 1，向量路排第 20：

- `both`（两路都中）：1/61 + 1/80 ≈ **0.0289**
- 另一文档：仅 BM25 第 3：1/63 ≈ **0.0159**

→ 两路交叉确认的文档稳赢单路冠军。这就是为什么前端把 `source=both`（混合）的命中排前面时看起来特别合理——RRF 本身就在奖励「两路一致」。

## 4. 为什么恰好是 60

没有数学推导，**经验值**：出自 RRF 的原始论文（Cormack et al., 2009），他们在多组数据集上试出来 60 最鲁棒（区间 0~1 上表现差别不大，60 处于对各种语料都不错的平台期），此后成了行业默认值。配上本项目的 `RRF_POOL=50`（每路最多取 50 名参与融合），k=60 保证即使排到第 50 名，贡献 1/110 也不是噪声量级——融合排序在整个候选池上都有区分度。

一句话总结：**RRF_K=60 = 「各路只比名次不比分值，60 是让头部优势平滑衰减的行业标准平滑常数」**。
