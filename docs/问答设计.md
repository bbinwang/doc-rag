# 问答设计 —— 全库检索、每模式独立 LLM、三参数、失败隔离、引用契约

> 本文回答：问答为什么是独立页全库检索而不是选中文档提问？为什么每模式独立调一次 LLM？三个可调参数各自卡在哪一环？答案里的 [n] 如何保证可追溯？
> 实现：`backend/src/main/java/com/docrag/ask/`（LlmClient、AskService、AskParams 等）。决策来源见《[adr/0001](adr/0001-问答重构为全库chunk级检索与每模式独立LLM.md)》。

## 1. 编排全链路

```
前端问答页 (ask.js)
    │  POST /api/ask { question, modes, bm25Chunks, vectorChunks, contextChunks }
    ▼
AskParams.effectiveParams(配置默认, 请求覆盖) → 钳制 [1,20]   ← 单点计算生效值
    ▼
AskService.ask()：遍历选中模式（LinkedHashMap 保序）
    ├─► ModeSearcher.recallChunks(question, bm25Chunks, vectorChunks)   ← 见《检索与召回》§3
    ├─► trimToBudget(selected, contextChunks, charBudget)   ← 贪心装填（超预算块跳过不终止）
    ├─► 拼 prompt：system（仅依据资料作答、引用标 [n]、资料不足须明说）
    │              + 编号资料（头行 [n] filename；deep 表格块自带「表格 N」标题行）+ user 问题
    └─► LlmClient.chat(system, user)   ← OpenAI 兼容 /chat/completions，非流式
    ▼
AskResponse { model, params, modes: { plain: {...}, deep: {...} } }
```

LLM 连接配置为多 provider 结构：`docrag.llm.providers.<name>.*` 维护多份连接参数，`docrag.llm.active` 选出唯一启用者（yml 现维护 `glm` 默认启用、`mac-uni` 保留不启用），响应 `model` 回显当前 provider 的模型名。详见《[运维与启动](运维与启动.md)》§5。

## 2. 设计取舍

### 2.1 为什么独立页 + 全库检索（而非选中文档提问）

旧设计「搜索页勾选文档 → 限定 docIds 检索作答」有两个问题：一是用户得先搜对、选对，检索失误直接传导为问答失误；二是「选文档」这个动作与「问问题」的心理模型冲突——用户想知道答案，不想先当检索员。全库 chunk 级混合召回把检索责任交还给系统，语义召回（词面不重叠也能命中）恰好补上人工选文档覆盖不到的盲区。

### 2.2 为什么每模式独立调一次 LLM（双模式 = 两次调用）

旧设计合并两模式上下文单次调用，答案里两模式的证据混在一起无法归属。独立调用后：

- plain 与 deep 的答案**天然可对比**（前端两栏），哪种解析模式更答得准一目了然；
- 失败隔离免费获得——deep 的 LLM 调用挂了，plain 照常出答案；
- 代价是双模式延迟翻倍（前端 `ASK_TIMEOUT=180s` 兜住串行两次调用）与 token 翻倍，本地场景可接受。

### 2.3 三参数：各卡一环，全部可调

| 参数 | 默认 | 卡在哪一环 | 配置项 |
|---|---|---|---|
| `bm25-chunks` | 5 | BM25 路 chunk 召回上限（doc 池 = clamp(该值, 5, 20) 篇） | `docrag.ask.bm25-chunks` |
| `vector-chunks` | 5 | 向量路 topK | `docrag.ask.vector-chunks` |
| `context-chunks` | 8 | RRF 融合重排后送 LLM 的 chunk 上限 | `docrag.ask.context-chunks` |
| （`context-char-budget`） | 6000 | 每模式上下文总字符预算 | `docrag.ask.context-char-budget`，**不开放请求覆盖** |

- 请求级覆盖（`Integer`，null = 配置默认）→ 后端统一钳制 [1, 20] → 生效值经 `params` 回显——`effectiveParams` 单点完成，前端问答页可按次实验调参。
- 截断策略：按融合序（词锚定优先、组内 RRF 降序，见《检索与召回》§3）贪心装填，撞 contextChunks 条数即停；单块超剩余字符预算**跳过该块继续装填**——deep 整 sheet 原子表块可能数万字符，「一票否决」会把该模式上下文清零，跳过后其余正常尺寸块仍能进入 LLM 上下文。**注意：截断会重排 ref 编号**——ref 按最终送入 LLM 的顺序编，与 chunks 返回顺序一致。

### 2.4 引用契约：ref ↔ [n] 一一对应

- prompt 中每份资料带编号头行 `[n] filename`，system 要求答案引用标 `[n]`；响应 `chunks[].ref` 即该编号——**答案中每个 [n] 都能映射回真实送入 LLM 的 chunk**。
- 禁止返回未送入的 chunk：截断发生在拼 prompt 之前，`chunks` 数组就是 prompt 资料清单本身，不存在「引用了但没给」或「给了但没引用」的展示侧歧义。
- deep 表格块的 `title`（「表格 N」）来自统一文本的标题行（见《[解析与入库](解析与入库.md)》§3.1），块文本自带语义头。

## 3. 失败语义矩阵

| 情形 | 行为 | HTTP |
|---|---|---|
| LLM 未配置（`docrag.llm.active` 空 / 指向不存在的 provider / 其 api-key 空） | 不发起任何调用 | 400 |
| 某模式召回 0 chunk | 该模式返回占位提示「未检索到…无法作答」，**不调 LLM**，另一模式照常 | 200 |
| 某模式 LLM 调用失败 | 该模式 `answer=null + error`，**chunks/docs 照常返回**（供调试），另一模式照常 | 200 |
| 全部选中模式 LLM 失败 | 整体失败 | 500 |
| 向量服务不可用 | 该模式 `degraded=true`，BM25 路 chunk 照常作答 | 200 |

原则：**不降级编造答案**——LLM 失败就明说失败，chunks 明细照给，让失败可诊断。答案与召回的对应关系（`chunks[].ref`）见 §2.4；检索侧召回细节见《[检索与召回](检索与召回.md)》。
