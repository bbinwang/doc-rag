# 解析与入库 —— 双模式解析、统一文本契约、切块算法、四库写入与回滚

> 本文回答：plain / deep 两模式各把文档变成什么文本？统一文本靠哪几条不变量支撑表格切块？Chunker 怎么切？入库顺序为什么是「本地先写、外部后写」？
> 实现：`backend/src/main/java/com/docrag/` 下 `parser/`（plain）、`deepmd/`（deep）、`indexer/`（切块与写入编排）。

## 1. 为什么是「双模式对称」而不是「一个库加 mode 字段」

plain 与 deep 的 content 是**两种不同粒度的文本**（拍平纯文本 vs 正文+markdown 表格混排），检索行为、切块策略、向量语义空间都随之不同。选型是把两种解析各自做成**完全对称的独立库**——各自一套 Lucene 倒排（`data/index-plain/`、`data/index-deep/`）+ 各自一个向量 collection（`docrag_plain` / `docrag_deep`）：

- 每个模式可独立删除重建（目录互不牵连）、独立降级、独立清理；
- `ModeIndexer` / `ModeSearcher` 一套类两实例共用，schema 完全同构，只差 content 来源——**结构对称换来了代码零分叉**；
- 代价是存储翻倍与上传双模式时写两遍，本地单机场景可接受。

对比方案「单索引 + mode 字段过滤」会把两种分词/高亮/切块策略搅进同一套查询路径，复杂度前移到检索侧，且无法独立重建。故弃。

## 2. plain：纯文本提取（`parser/`）

| 格式 | 实现 | 提取约定 |
|---|---|---|
| docx | POI `XWPFWordExtractor.getText()` | 段落与表格文本由 extractor 内部拼接，无自定义分隔 |
| xlsx | POI `WorkbookFactory` + `DataFormatter` | 每 Sheet 前加 `## Sheet名` 标题行；行内单元格 `\t` 分隔；`DataFormatter` 保持显示格式、**不求值公式** |
| pdf | PDFBox `PDFTextStripper` | 仅文本型；提取结果为空 → 判定扫描件，400（无 OCR） |

解析失败统一包成 `DocumentParseException` → API 400（「文件可能已损坏或加密」），不 500。

## 3. deep：统一文本（`deepmd/`）

统一文本 = **正文段落与 markdown 表格按文档原始顺序拼接**的单一文本流。三种格式策略不同：

- **docx**（`DocxDeepmdExtractor`）：按 `getBodyElements()` 顺序遍历——段落逐行累积；表格前补空行、输出「表格 N」标题行（N 按 body 顺序递增，空表跳过但编号仍递增）+ markdown 表格、表格后补空行。
- **xlsx**（`XlsxDeepmdExtractor`）：每个非空 sheet 一块 = sheet 名标题行 + **完整 markdown 表格（首行作表头，不分片）**，sheet 间空行。读数方式与生产 `XlsxParser` 一致（同 `DataFormatter`、同空行剔除）。
- **pdf**（`PdfDeepmdExtractor`）：PDF 无内建表格结构，整体纯文本即统一文本（与 plain 同文），`tableCount=0`，**不做启发式猜表**——猜错的表格比没有表格更害检索。

### 3.1 统一文本三不变量（deepmd 与 Chunker 的共同契约）

1. **块之间恰好一个空行**——空行是可靠的块边界；
2. **表格标题行与表格紧连（无空行）**——保证切块时「标题+表格」整体保留；
3. **markdown 单元格内不含换行**（`MarkdownTable` 转义：`\r`→空格、`\n`→空格、`|`→`\|`、单元格 trim）——表格内部不可能出现空行，空行语义不被污染。

**为什么这三条是契约**：`chunkKeepingTables` 完全靠「空行分块 + 管道行识别表格」两个纯文本信号工作，不携带任何结构化元数据。任何一条被破坏（比如单元格内混入换行），切块就会把一张表腰斩或把两块粘成一块。**改 deepmd 拼接规则必须同步验证 Chunker**，反之亦然。

`tableCount`（docx=表格数 / xlsx=非空 sheet 数 / pdf=0）仅用于上传响应展示，**不入索引 schema**——它不是检索信号，存进倒排只占空间。

## 4. Chunker：切块算法（`indexer/Chunker.java`）

| 常量 | 值 | 含义 |
|---|---|---|
| `MAX_CHARS` | 128 | plain 向量块上限（`chunk()` 默认） |
| `DEEP_EMBED_MAX_CHARS` | 256 | deep 向量块上限（`chunkKeepingTables` 用） |

**256 的出处**：bge-small-zh-v1.5 输入上限 512 token，中文约 1 字 ≈ 1 token，非表格块取 256 字符留出安全余量；128 则是 plain 纯文本更细粒度的经验值（块越小命中越准，向量数越多）。

### 4.1 `chunk(content, maxChars)` — 三级策略

1. 按 `\n` 切段，空段丢弃；段长 ≤ maxChars → 直接成块；
2. 长段按句末标点（`。！？；!?;`，标点随句保留）切句，句子累积进缓冲，放不下先 flush；
3. 无标点的超长串（如长 URL/编号）→ 硬切 maxChars。

### 4.2 `chunkKeepingTables(content, maxChars)` — 块感知

1. 先按空行（`\n\s*\n`）切块——这一步就把「标题+表格」天然分在一起（不变量 2）；
2. 块内**任一行 strip 后以 `|` 开头 ⇒ 整块原样保留不切**（可能超 maxChars，由调用方预算取舍）——保证表格自含表头行，半张表对向量检索毫无意义；
3. 纯文本块剥掉首尾空白后再走 `chunk()` 细切。

### 4.3 为什么「检索期切块必须 = 入库期切块」

问答链路（`recallChunks`）的 BM25 路在查询时对全库文档重新切块，与向量库 chunk 做 `(docId, chunk 精确文本)` **精确文本去重**后 RRF 融合。两套切块若有一个字节差异，同一 chunk 会被当成两个不同 chunk——去重失效、RRF 排名失真。因此 `IngestService` 与 `ModeSearcher.chunkForMode` 调用**同一个 `Chunker` 的同一个方法与参数**（plain=`chunk`、deep=`chunkKeepingTables(256)`）。**改切块策略必须两侧同步改**。

## 5. IngestService：写库顺序与回滚（`indexer/IngestService.java`）

```
上传流 readAllBytes() 进内存（multipart 流不可回读，多模式共用）
  → fail-fast：选中模式全部解析成功才进写库（半途解析失败零写入）
  → per-mode 切块（plain: chunk(128) / deep: chunkKeepingTables(256)）
  → 写库顺序：plain 倒排 → deep 倒排 → plain 向量 → deep 向量
      每步成功即向 rollbacks 登记一个撤销 Runnable
  → 任一步抛异常：逆序执行 rollbacks，包成 IllegalStateException 上抛
```

设计取舍：

- **本地先写、外部后写**：Lucene 写入几乎不会失败（本地文件），vector-service 是跨进程 HTTP、最可能挂的一环放最后——失败时前面要回滚的都是自己可控的本地操作。
- **逆序回滚**：撤销顺序与写入相反，保证任何时刻系统状态是「某前缀完整写入」或「全无」。
- **回滚失败只 log.warn 不吞原始异常**：回滚本身失败（如 vector-service 恰在此刻恢复/又挂）不能掩盖导致失败的根因；残留数据靠幂等 upsert（`id`=docId）与级联删除兜底。
- **倒排幂等 upsert**：`updateDocument(Term("id", docId))`，重传同名文件覆盖而非重复；写后 commit + `maybeRefreshBlocking()` 近实时可见。

## 6. 索引 schema（两模式同构，一文一 Document）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | StringField(Store.YES) | docId（UUID），级联删除键 |
| `filename` | TextField(IK) | 参与检索 |
| `path` | StringField | 存储路径 |
| `type` | StringField | docx / xlsx / pdf |
| `modified` | StoredField | 上传时间戳（毫秒） |
| `content` | TextField(IK) | plain=纯文本 / deep=统一文本；存储以供高亮与明细展示 |
